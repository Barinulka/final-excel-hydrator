# Investments Implementation Plan

## Назначение документа

Этот файл фиксирует рабочий план реализации блока `Investments`.

Он нужен для того, чтобы:

* не терять границы текущего этапа;
* не смешивать в одном шаге ввод данных, график финансирования и расчетный backend;
* понимать, что уже сделано, что в работе, а что сознательно отложено;
* двигаться маленькими вертикальными slices, как это было сделано для `TimeParams`.

Этот документ не заменяет:

* [domain-model.md](./domain-model.md)
* [storage-model.md](./storage-model.md)
* [use-cases.md](./use-cases.md)

Он описывает именно порядок реализации.

---

## Цель блока Investments

`Investments` — это отдельный доменный блок `FinancialModel`, который отвечает за:

* первоначальные инвестиции;
* капитальные вложения;
* расходы будущих периодов;
* первоначальный оборотный капитал;
* график финансирования по месяцам инвестиционной фазы;
* подготовку данных для backend-расчетов, summary и Excel export.

На уровне архитектуры `Investments` не должен сводиться к одному большому JSON blob и не должен проектироваться от UI-формы.

---

## Принцип реализации

Реализуем `Investments` поэтапно:

1. сначала реестр инвестиционных строк;
2. потом план-график / финансирование;
3. потом расчетные таблицы backend;
4. потом отложенные расширения.

Это важно, потому что ТЗ по CAPEX описывает сразу несколько разных уровней системы:

* ввод пользовательских данных;
* выбор периодов финансирования;
* расчет производных таблиц;
* будущие налоговые и ремонтные расширения.

Если делать все сразу, границы домена быстро размоются.

---

## Что входит в Investments

В реализацию блока входят:

* `InvestmentBlock` как aggregate root блока инвестиций внутри `FinancialModel`;
* `InvestmentItem` как пользовательская инвестиционная строка;
* code-defined `InvestmentCategory`;
* code-defined `InvestmentGroup`;
* code-defined `InvestmentTreatment`;
* `InvestmentSchedulePeriod` для отмеченных месяцев финансирования;
* read models для вкладки Investments;
* backend calculations, которые используют `Investments` и `TimeParams`.

---

## Что не делаем сразу

На первом этапе не делаем:

* ремонтную программу;
* полноценный блок налогообложения;
* ручное независимое редактирование таблицы финансирования;
* квартальную и годовую агрегацию `Investments`;
* произвольные пользовательские категории;
* универсальный конструктор CAPEX-форм;
* сложные графики и аналитику до завершения базового backend slice.

---

## Реализация по slices

## Slice 1. Реестр инвестиций

### Цель

Дать пользователю возможность:

* открыть вкладку `Investments`;
* увидеть code-defined группы и категории;
* добавить инвестиционную строку;
* отредактировать строку;
* удалить строку.

### Что входит

* enum-ы:
  * `InvestmentGroup`
  * `InvestmentTreatment`
  * `InvestmentCategory`
* доменные сущности:
  * `InvestmentBlock`
  * `InvestmentItem`
* Doctrine entities / mapping:
  * `investment_blocks`
  * `investment_items`
* use cases:
  * `GetInvestmentsPage`
  * `AddInvestmentItem`
  * `UpdateInvestmentItem`
  * `DeleteInvestmentItem`
* API request/response DTO
* page builder для вкладки `Investments`
* tab provider для `Investments`
* первый UI вкладки с категориями и формой редактирования строки

### Что не входит

* schedule financing;
* таблица финансирования;
* НЗС;
* амортизация;
* списание РБП;
* Excel-like monthly matrix;
* графики.

### Ключевая модель

На этом этапе:

* верхний уровень задается кодом, а не таблицей в БД;
* `Капитализируемые затраты` и `Первоначальные затраты перед запуском` — это `InvestmentGroup`;
* конкретные пользовательские строки — это `InvestmentItem`;
* обязательность полей определяется категорией.

### Статус

`planned`

### Ближайший подшаг

* создать enum-ы `InvestmentGroup`, `InvestmentTreatment`, `InvestmentCategory`

## Slice 2. План-график / финансирование

### Цель

Дать пользователю возможность отметить месяцы инвестиционной фазы, в которых финансируется каждая инвестиционная строка.

### Что входит

* сущность / storage:
  * `InvestmentSchedulePeriod`
  * `investment_schedule_periods`
* use cases:
  * `GetInvestmentSchedule`
  * `UpdateInvestmentSchedule`
* валидация по `TimeParams`
* распределение суммы по отмеченным месяцам
* backend read model для таблицы финансирования
* UI выбора месяцев инвестиционной фазы

### Правила этапа

* доступны только месяцы инвестиционной фазы из `TimeParams`;
* пользователь отмечает один или несколько месяцев;
* сумма периода не хранится напрямую, а рассчитывается на backend;
* если `TimeParams` изменились и часть schedule вышла за пределы инвестиционной фазы, блок считается требующим исправления, но данные не удаляются автоматически.

### Что не входит

* ручное независимое редактирование финансирования;
* НЗС;
* амортизация;
* списание РБП;
* Excel export payload.

### Статус

`planned`

---

## Slice 3. Backend calculations

### Цель

Построить первый расчетный backend layer поверх `Investments` и `TimeParams`.

### Что входит

* расчет первоначальной стоимости с учетом НДС;
* расчет финансирования по периодам;
* НЗС:
  * на начало периода
  * поступление
  * постановка на баланс
  * на конец периода
* амортизация по строкам с treatment `capexDepreciable`;
* списание расходов будущих периодов;
* агрегированные итоговые строки;
* read models для summary / таблиц / Excel preparation.

### Зависимости

Этот slice должен использовать:

* сохраненные `InvestmentItem`;
* `InvestmentSchedulePeriod`;
* `TimeParams`;
* `TimelineCalculator`.

### Что не входит

* полноценный блок налогообложения;
* ремонтная программа;
* AI summary;
* сложные фронтовые графики.

### Статус

`planned`

## Порядок работы внутри каждого slice

Для каждого следующего slice работаем в одном и том же порядке:

1. уточнение доменной части внутри slice;
2. проверка storage model;
3. фиксация use cases;
4. backend implementation;
5. tests;
6. page layer / API;
7. UI.

UI не должен становиться местом, где проектируется домен.

## Открытые вопросы

На будущее нужно будет уточнить:

* появится ли отдельный `Taxation` block до полноценного CAPEX calculation slice;
* где будет храниться ставка НДС после появления налогового блока;

* как лучше показывать невалидный график после изменения `TimeParams`.
